# 仕様書の書き方

仕様書は、アプリが外から見て何をするかを決める文書。実装を一言一句文章に置き換えることは、仕様書に求めていることからもっとも遠い。コードを日本語に訳した文は、コードを読めば分かることしか伝えず、実装を変えるたびに直す手間だけを増やす。

## 書くこと・書かないこと

書くのは、クライアント・メンバー・管理者・Tapなど、アプリの外から観測できる結果だけ。応答の中身、画面の表示、保存するかしないか、エラーがこれに当たる。

次は書かない。

- 処理の手順や順序、条件分岐や計算式をそのまま写したもの
- ジョブ、キュー、トランザクション、ロックなど、結果を出すための仕組み
- 関数名、クラス名、列名、ファイルパス
- 再試行の回数や待ち時間などの調整値。値に意味があるときだけ、理由と一緒に地の文に書く

迷ったら「実装をすべて書き直しても、この文は変わらないか」と考える。変わるなら実装の説明なので、その実装で実現したい結果を書く。

| 実装をなぞった文                                                         | 仕様にした文                                        |
| ------------------------------------------------------------------------ | --------------------------------------------------- |
| 閲覧者とその保存済みのフォロー先をTapに追加するジョブを積む              | 閲覧者とその保存済みのフォロー先をTapに追加する     |
| moreRepliesに、replyCountから含めたリプライ数を引いた数(0未満は0)を返す  | moreRepliesに、含めなかったリプライの数を返す       |
| バックフィルのレコードから積むジョブは、ライブのものより低い優先度で積む | バックフィル中も、ライブのレコードを先に保存する    |
| appviewで見えるまで1秒おきに5回まで待ってから画面を更新する              | 投稿がappviewで見えるようになってから画面に表示する |

## 仕様項目

- 1項目に1つの振る舞いを書く。「〜し、〜する」と2つの振る舞いがつながったら分ける(例: 並び順とcursorによるページ送り)
- 「〜の場合、〜を返す」というテストの条件ではなく、「〜する」「〜は含めない」という振る舞いのルールにする
- 1項目は1つのテストで確かめられる大きさにする。入力のパターンを1つずつ項目にせず、規則として1文にまとめる
- 正確さより読みやすさを優先して簡潔に書く。実装の全パターンを文章にせず、仕様を理解するための文にする

## 理由と補足

テストできない記述は、IDを付けずに表の下の地の文に書く。表にできるものは表にする。

- なぜその仕様なのかを書く。後から読む人が、仕様を変えてよいかを判断できるようにするため
- 公式AppViewと違う挙動、保存しないもの、見送った機能には、必ず理由を書く
- 理由は実装を変えても成り立つものにする。DBの容量、公式クライアントとの互換性、運用の負荷などは理由になる。「既存のコードがこうなっているから」は理由にならない

## 形式

- docs/specs の worker・web・appview 以下の、機能ごとのファイルに書く。1ファイルは1アプリの振る舞いだけを定める
- 見出しはAPIの名前か機能・画面の名前にし、直後にその機能が何をするかを1〜2文で書く
- 仕様項目は「ID」と「仕様」の2列の表に書く
- IDは`{見出しの短い名前}-{連番}`とし、短い名前はcamelCaseにする(例: getTimeline-1)
  - webは、E2Eなら`-e{連番}`、playなら`-s{連番}`にする(例: login-e1, login-s1)
  - 連番は見出しごと(webはeとsそれぞれ)に、追加した順に振る。項目を削除しても詰めず、並び順も問わない
- コード表記は画面のURL、環境変数名、デプロイ手順のコマンドだけにする。lexiconの名前や項目名は地の文で書く

## 実装を変えるとき

- 振る舞いが変わるなら、同じPRで仕様書を直す。対応する仕様書がなければ新しく書く
- 振る舞いが変わらないリファクタリングでは、仕様書は変わらない。変える必要があるなら、その仕様書は実装をなぞっている
- 仕様IDは変えない。項目の文を変えたら、同じPRでテスト名の文も合わせる
- 仕様書はコードと食い違っていることがある。コードと照らし、疑わしい記述はユーザーに確認する
