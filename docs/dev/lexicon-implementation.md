# Lexiconレコードのインデックス実装ガイド

新しいレコードタイプ（例: app.bsky.graph.list）をworkerでインデックスするときの流れです。迷ったら、app.bsky.graph.followの実装をなぞってください。

## データの流れ

workerは、Tapから受け取ったレコードもPDSから取得したレコードも、IndexRecordServiceの1つの流れで処理します。レコードタイプごとに分かれるのは、変換と保存（SaveRecordService）だけです。保存するか、何を取得するか、誰に通知するか、何を集計し直すかは、関心ごとの規則ファイルがまとめて決めます。

## 手順

| 順  | やること                                                                         |
| --- | -------------------------------------------------------------------------------- |
| 1   | Lexicon定義を取得し、クライアントのコードを生成する。定義ファイルは手で書かない  |
| 2   | データベースにテーブルを追加し、マイグレーションを作る                           |
| 3   | レコードをDBに依存しない型に変換する処理を作り、対応するコレクションの一覧に足す |
| 4   | Repositoryのインターフェースと実装、テスト用のインメモリ実装を作る               |
| 5   | SaveRecordServiceに保存の分岐を足す                                              |
| 6   | RepositoryをDIに登録し、テストではインメモリ実装に差し替える                     |
| 7   | 規則ファイルに必要な行を足す                                                     |
| 8   | 変更したサービスとRepositoryのテストを書き、pnpm allを通す                       |

規則ファイルは次の5つです。どれも値を返すだけで、ジョブの予約はIndexJobServiceの1か所で行います。

| 規則                      | 決めること                                   |
| ------------------------- | -------------------------------------------- |
| StoragePolicyService      | 保存するかどうか                             |
| FetchPolicyService        | PDSから取りに行くレコードとハンドル          |
| NotificationPolicyService | 作る通知                                     |
| StatsPolicyService        | 保存・削除のあとに集計し直す投稿とアカウント |
| TrackingPolicyService     | 保存・削除のあとに追跡を見直すアカウント     |
