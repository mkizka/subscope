# リポジトリとクエリサービス

## テーブルの分け方

テーブルは、行の寿命と、行を変えるきっかけ(書く処理)で分ける。

- 1つのテーブルの1行は、1つのモデルを1回の保存でまるごと書く単位にする
- 行ができたあとに変わる項目は、変えるきっかけが1つになるようにテーブルを分ける。きっかけが2つある行は、互いに古い値で上書きし合う
- 行を作るときに決まり、そのあと変わらない項目は、寿命が同じ行に一緒に置いてよい
- 「ある間だけ有効」な状態(追跡中、管理者など)は、カラムの値ではなく行のある・なしで表す。始まりで行を作り、終わりで行を消す
- 一緒に読むことは、同じテーブルにする理由にしない。テーブルをまたぐ読み取りはクエリサービスが行う
- 寿命ときっかけが同じものを、1対多などの形の都合で別のテーブルにするのはかまわない

時刻のカラムは `createdAt` のような汎用的な名前にせず、`trackedAt`(追跡を始めた時刻)のように何が起きた時刻かが分かる名前にする。

## リポジトリ

ドメインモデルを保存するための入れ物。メソッドは次の3つだけにする。

| メソッド | 役割                              |
| -------- | --------------------------------- |
| find     | キーでドメインモデルを1つ取り出す |
| save     | ドメインモデルを保存する          |
| delete   | ドメインモデルを削除する          |

部分更新もメソッドを増やさず、取り出したドメインモデルを変えて保存する。競合を防ぎたいときは、まずテーブルを分けて、変えるきっかけを1つにする。それでも同じ行を2つの処理が変えるときだけ、取り出すときに行をロックするか、保存するときに古いデータで上書きしないようにする。

保存するものは、守る決まりや判定の決まりがあればドメインモデル、なければ単純な型にする(判断の基準は `.claude/skills/domain-model/SKILL.md`)。application層はDBのスキーマに依存せず、DBへの変換はinfrastructure層が受け持つ。

## クエリサービス

存在確認・一覧・集計・検索など、更新のためではない読み取りはクエリサービスに書く。

クエリサービスはドメインモデルを返さず、用途ごとに分けた単純な型を返す。ドメインモデルは更新するために取り出すものなので、読み取りで返すと役割が混ざる。1つの型に項目を足していくと、使わない項目のために読み取りが重くなるので、呼び出し側が使う項目だけを持たせる。

## トランザクション

ユースケースは、読み取りだけや1回書くだけでも、トランザクションを作ってからリポジトリやクエリサービスに渡す。書き方を1つにしておけば、あとで書き込みが増えても包み直さずに済む。

DIDの解決やTapへの問い合わせなど外部への通信はトランザクションの外で行い、その前後の読み書きを別々のトランザクションにする。
