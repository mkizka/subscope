# Workerのチューニング

Workerの並列数、DB接続数、レート制限とその理由。外から見える振る舞いではなく、運用で調整する値を扱う。

## Tapのイベント

Tapのイベントは`TAP_CONCURRENCY`(既定64)件まで並列に処理し、DBの接続は`DATABASE_POOL_MAX`(既定32)本まで使う。appviewとwebの接続(各10本)と、デプロイ時に新旧のWorkerが並ぶ間を合わせても、PostgreSQLの既定の上限(100本)に収まるようにしている。

## 外部への問い合わせ

外部へ問い合わせる`fetchRecord`と`resolveDid`のジョブは1件に1秒前後かかるため、それぞれ20件と8件まで並列に処理する。問い合わせ先の負荷を抑えるために、件数は毎秒10件と4件までに制限する。初回同期ではフォロー先のフォロー先など大量のアカウントが見つかり、処理に何時間もかかるため、新しく登録したアカウントなどライブのジョブを先に処理する。

## 集計

アカウントの集計ジョブは16件まで並列に処理する。バックフィルでは集計ジョブが大量に積まれるため、1件ずつでは消化に何時間もかかる。投稿の集計ジョブは1件ずつ処理し、1回のSQLで1000件までの投稿をまとめて数え直す。
