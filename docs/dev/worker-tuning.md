# Workerのチューニング

Workerの並列数、DB接続数、レート制限とその理由。外から見える振る舞いではなく、運用で調整する値を扱う。

| 対象                      | 値                                                                                                                  | 理由                                                                                                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tapのイベント             | 16件まで並列に処理し、DB接続は `DATABASE_POOL_MAX`(既定32)本まで使う                                                | 1件ずつでは毎秒約55件しか処理できず、大きいアカウントのバックフィル中に他のメンバーの新着が止まったため。DB接続はappviewとwebの接続(各10本)と、デプロイ中に新旧のWorkerが並ぶ間を合わせても、PostgreSQLの既定の上限(100本)に収めるため |
| Jetstreamのイベント       | 1件ずつ処理する。メンバーと追跡アカウントの一覧はメモリに持ち、1分おきにDBから読み直す。受信位置は5秒おきに保存する | 毎秒数百件届くイベントのほとんどを、DBを読まずに捨てるため。一覧は登録やフォローのたびに書き換えるので、読み直しは書き換えが漏れたときの保険                                                                                           |
| レコードの取得とDIDの解決 | それぞれ20件と8件まで並列に処理し、毎秒10件と4件までに制限する                                                      | 1件に1秒前後かかるが、問い合わせ先の負荷は抑えたいため                                                                                                                                                                                 |
| アカウントの集計          | 16件まで並列に処理する                                                                                              | バックフィルで大量に積まれ、1件ずつでは消化に何時間もかかるため                                                                                                                                                                        |
| Tapの初回同期             | `TAP_RESYNC_PARALLELISM` で2件まで並列にする(Tapの既定は5件)                                                        | 1件ごとにリポジトリ全体をメモリに載せ、Workerが受け取り終えるまで保持する。並列5件では大きいリポジトリが重なるとTapのメモリが8GB近くまで増えたため                                                                                     |
| 投稿の集計                | 1件ずつ処理し、1回のSQLで1000件までの投稿をまとめて数え直す                                                         |                                                                                                                                                                                                                                        |

初回同期ではフォロー先など大量のアカウントが見つかり、処理に何時間もかかる。そのため、新しく登録したアカウントなどライブのジョブを先に処理する。
