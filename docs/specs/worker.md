# Worker仕様

用語は[用語集](../glossary.md)を参照する。

## Tapからのイベント受信

Tapからイベントを受け取り、recordイベントではレコードをインデックスし、identityイベントではアカウントの状態を保存する。

| ID        | 仕様                                                                                    |
| --------- | --------------------------------------------------------------------------------------- |
| channel-1 | イベントは処理を終えてからTapにackする                                                  |
| channel-2 | サポートしないコレクションのrecordイベントは、保存せずにackする                         |
| channel-3 | DBに保存できなかったイベントはackしない                                                 |
| channel-4 | スキーマに合わないレコードなど、処理しないと決めたイベントはackする                     |
| channel-5 | 処理中のイベントが`TAP_CONCURRENCY`(既定64)件に達したら、空くまで次のイベントを読まない |

ackしなかったイベントは、Tapがしばらくしてから再送する。Tapはリポジトリごとにイベントの順序を守るので、処理しないイベントもackしないと、そのリポジトリのイベントが止まってしまう。読むのを止めている間、待っているイベントはTapに溜まる。

## レコードのインデックス

Tapから受け取ったレコードをDBに保存・削除する。対象は投稿、リポスト、いいね、フォロー、プロフィール、フィード、リスト、リストの項目、threadgate、postgate。

| ID       | 仕様                                                                         |
| -------- | ---------------------------------------------------------------------------- |
| index-1  | 作成・更新されたレコードを保存する                                           |
| index-2  | 削除されたレコードを削除する                                                 |
| index-3  | スキーマに合わないレコードは保存しない                                       |
| index-4  | null文字を含むレコードは保存しない                                           |
| index-5  | 削除したレコードを、それより古いコミットで復活させない                       |
| index-6  | 更新したレコードを、それより古いコミットで古い内容に戻さない                 |
| index-8  | 処理済みと同じrevのコミットは、もう一度処理する                              |
| index-9  | threadgateとpostgateは、同じアカウントの同じrkeyの投稿に付くものだけ保存する |
| index-10 | 保存済みのアカウントは、ハンドルと状態が変わらなければ更新しない             |
| index-11 | いいねは、いいねした人かいいねされた投稿の作者がメンバーのものだけ保存する   |
| index-12 | バックフィルのレコードから積むジョブは、ライブのものより低い優先度で積む     |
| index-13 | アカウントを保存するときは、管理者権限を書き換えない                         |
| index-14 | 保存しないレコードのコミットは、revを記録しない                              |
| index-15 | 投稿のgallery埋め込みの画像を、images埋め込みと区別して保存する              |
| index-16 | 投稿のvideo埋め込みのメタデータを保存する                                    |

| 対象                 | 理由                                                                                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| null文字             | null文字を含む文字列はPostgreSQLに保存できない                                                                                                                                         |
| rev                  | コミットは届いた順に処理されるとは限らないので、レコードごとに処理済みの最新のrevを記録する。同じrevを処理し直すのは、後続のジョブを積む前に失敗しても、再送で積み直せるようにするため |
| threadgate・postgate | threadgateとpostgateは対象の投稿と同じrkeyを持つので、appviewは投稿から引ける                                                                                                          |
| アカウントの更新     | アカウントの更新は行ロックを取るので、同じアカウントのコミットが続くバックフィルでロック待ちが起きる                                                                                   |
| いいね               | いいねは件数が多く、フォロー先の分まで保存するとDBが大きくなる。ActivityPubでも、いいねは本人と投稿の作者のサーバーにしか届かない                                                      |
| 管理者権限           | 管理者権限はappviewだけが書き換える                                                                                                                                                    |
| 動画                 | 動画の本体は保存せず、再生には公式の動画サーバーを使う。字幕は保存しない                                                                                                               |

## レコードの取得

インデックス中に必要になった、保存していないレコード(引用された投稿など)をPDSから取得して保存する。

| ID            | 仕様                                                                |
| ------------- | ------------------------------------------------------------------- |
| fetchRecord-1 | PDSにレコードがなければ、再試行せずに終える                         |
| fetchRecord-2 | PDSにリポジトリがないか、停止・凍結されていれば、再試行せずに終える |
| fetchRecord-3 | DIDが登録されていなければ、再試行せずに終える                       |
| fetchRecord-4 | それ以外の失敗では再試行する                                        |

結果が変わらない失敗で再試行すると、失敗したジョブがキューに溜まり続ける。DNSの失敗や5xxの応答などは一時的なことがあるので再試行する。

## キュー件数のログ

ジョブの滞留を確認できるように、キューごとの件数を1分ごとにログへ出す。

## Tapへの追加

追跡アカウントをTapに追加して、そのレコードを受け取る。追跡アカウントかどうかが変わりうる操作のあとに、その時点のDBの状態から追加するか外すかを決める。

| ID    | 仕様                                                                          |
| ----- | ----------------------------------------------------------------------------- |
| tap-1 | メンバーがフォローしたアカウントをTapに追加する                               |
| tap-2 | メンバー以外のフォローではTapに追加しない                                     |
| tap-3 | メンバーがフォローを外したアカウントは、追跡アカウントでなくなればTapから外す |
| tap-4 | 他のメンバーがフォローしているアカウントはTapから外さない                     |
| tap-5 | メンバー以外がフォローを外してもTapから外さない                               |
| tap-6 | メンバーはフォローを外されてもTapから外さない                                 |

## バックフィルの状態の確認

Tapに追加したアカウントの過去のレコードを、Tapが同期し終えたかを確認して保存する。webはこれを読んで、メンバーにバックフィルが終わったかを知らせる。

| ID         | 仕様                                                                              |
| ---------- | --------------------------------------------------------------------------------- |
| backfill-1 | Tapに追加したアカウントのバックフィルの状態を確認する                             |
| backfill-2 | Tapの状態を、エラー・同期中・完了のどれかに分けて保存する                         |
| backfill-3 | 完了でなければ、間隔を伸ばしながら確認を続ける                                    |
| backfill-4 | 追跡アカウントでなくなったアカウントは確認しない                                  |
| backfill-5 | 起動時に、状態をまだ確認していない追跡アカウントを確認する                        |
| backfill-6 | リレーが削除済みと答えるエラーのアカウントは、Tapから外して完了とし、確認を止める |

| Tapの状態                          | 保存する状態 |
| ---------------------------------- | ------------ |
| error                              | エラー       |
| pending、desynchronized、resyncing | 同期中       |
| それ以外                           | 完了         |

Tapは失敗したバックフィルを自動で再試行するので、エラーでも確認を続ける。停止・凍結されたアカウントはこれ以上レコードが届かないので完了とみなす。確認の間隔は10秒から最長10分まで伸ばす。完了はTapが送り終えた時点なので、Workerが保存し終えるまでには数分かかる。

## モデレーションサービスからのラベル受信

`MODERATION_URL` のモデレーションサービスからラベルを受け取って保存する。既定はBluesky公式のモデレーションサービス。

| ID                | 仕様                                                                |
| ----------------- | ------------------------------------------------------------------- |
| subscribeLabels-1 | 受け取ったラベルを1件ずつ保存する                                   |
| subscribeLabels-2 | 最後に受け取ったラベルのseqを保存し、再接続時はその続きから受け取る |

seqはモデレーションサービスごとに保存するので、`MODERATION_URL` を変えると新しいサービスの今のラベルから受け取る。

## ラベルの保存

モデレーションサービスから受け取ったラベルを保存する。

| ID      | 仕様                                                                |
| ------- | ------------------------------------------------------------------- |
| label-1 | 保存済みのアカウントと、そのレコードに付いたラベルを保存する        |
| label-2 | 保存していないアカウントのラベルは保存しない                        |
| label-3 | negがtrueのラベルを受け取ったら、同じラベルを削除する               |
| label-4 | Tapに追加したアカウントに前から付いているラベルを取り寄せて保存する |

レコードに付いたラベルは、公式のモデレーションサービスがまとめての取り寄せに対応しないので、追跡を始めたあとに受け取った分だけを保存する。

## アカウント状態の保存

Tapのidentityイベントが持つアカウントの状態(active、deactivated、deleted、suspended、takendown)を保存する。

| ID        | 仕様                                                |
| --------- | --------------------------------------------------- |
| account-1 | アカウントの状態を保存する                          |
| account-2 | 状態が deleted のアカウントは、アカウントを削除する |

deleted は取り消せないので、レコードや登録も一緒に削除する。それ以外の状態は元に戻りうるので、データを残してappviewで隠す。

## ハンドルの解決

ハンドルを持たないか handle.invalid のアカウントについて、DIDドキュメントからハンドルを解決して保存する。

| ID           | 仕様                                                                                     |
| ------------ | ---------------------------------------------------------------------------------------- |
| resolveDid-1 | DIDドキュメントのハンドルは、同じDIDに解決できるときだけ保存する                         |
| resolveDid-2 | ハンドルが同じDIDに解決できないときは handle.invalid を保存する                          |
| resolveDid-3 | handle.invalid 以外のハンドルを持つアカウントは上書きしない                              |
| resolveDid-4 | Tapのidentityイベントのハンドルが handle.invalid のときは、DIDドキュメントから解決し直す |
| resolveDid-5 | DIDが登録されていないときは、再試行せずに終える                                          |

DIDドキュメントのハンドルは本人以外も書けるため、公式AppViewと同じく、ハンドルからDIDへ解決できるか確かめてから保存する。Tapも同じ検証をするので、すでにあるハンドルはTapを優先する。ただしTapは一時的な失敗でも handle.invalid を送るため、handle.invalid だけは自分で解決し直す。DIDが登録されていないときは再試行しても変わらないので失敗にせず、それ以外の失敗は再試行する。

`ATPROTO_HANDLE_RESOLVER_URL`を設定すると、ハンドルをDNSやHTTPSではなく、そのサーバーの com.atproto.identity.resolveHandle で解決する。.test のハンドルを使う開発環境向けの設定である。

## 統計の集計

いいね数やフォロワー数などの統計を、レコードのインデックス後にジョブで数え直す。ジョブは10秒遅らせて実行し、続けて来たイベントを1回にまとめる。

| ID          | 仕様                                                                                      |
| ----------- | ----------------------------------------------------------------------------------------- |
| aggregate-1 | 同じ対象のジョブが実行待ちの間に来たイベントは、そのジョブにまとめる                      |
| aggregate-2 | ジョブの実行中や完了後に来たイベントは、もう一度集計する                                  |
| aggregate-3 | 投稿のジョブが実行待ちの間に来た別の投稿のイベントも、そのジョブにまとめる                |
| aggregate-4 | アカウントのジョブは、フォロー・フォロワー・投稿のどのイベントから積まれても1つにまとめる |

バックフィルではいいねやリポストが多くの投稿に散らばって届くため、投稿の統計は投稿ごとにジョブを積まず、まとめて数え直す。

## 通知の生成

レコードをインデックスするときに、メンバー宛ての通知を作る。

| ID       | 仕様                                                                                                      |
| -------- | --------------------------------------------------------------------------------------------------------- |
| notify-1 | 通知はメンバー宛てにだけ作る                                                                              |
| notify-2 | 自分自身の操作では通知を作らない                                                                          |
| notify-3 | いいねされた投稿の作者に like の通知を作る                                                                |
| notify-4 | リポストされた投稿の作者に repost の通知を作る                                                            |
| notify-5 | フォローされたアカウントに follow の通知を作る                                                            |
| notify-6 | リプライの親投稿から4つ上までの投稿の作者に reply の通知を作る                                            |
| notify-7 | 引用された投稿の作者に quote の、メンションされたアカウントに mention の通知を作る                        |
| notify-8 | 1つの投稿から同じ相手への通知は mention、quote、reply の優先順で1件にする                                 |
| notify-9 | 通知はTapからリアルタイムに受け取ったレコードでだけ作り、バックフィルや取得しに行ったレコードでは作らない |

リプライの祖先は保存済みの投稿だけをたどるので、未保存の投稿より上の作者には通知しない。

v1.0では、追跡アカウント以外からの通知（Tapから受信しないため）と、上記以外の種類（starterpack-joined、verified、like-via-repost、subscribed-post など）は作らない。

## プッシュ通知の送信

通知を作ったときに、受け取るメンバーが登録した端末へ Web Push でプッシュ通知をジョブで送る。設計は[プッシュ通知の設計](../dev/push-notification.md)を参照する。

| ID     | 仕様                                                                            |
| ------ | ------------------------------------------------------------------------------- |
| push-1 | 送る前に取り消された通知は送らない                                              |
| push-2 | タイトルと本文を、通知の種類に合わせて設計書の表のとおりにする                  |
| push-3 | いいねとリポストは、同じ投稿への同じ種類の通知が端末上で1件にまとまるようにする |
| push-4 | プッシュサーバーが404か410を返した端末の登録を削除する                          |
| push-5 | 通知を新しく作ると、受け取るメンバーが登録したすべての端末に送る                |
| push-6 | すでに保存していた通知は、レコードの更新や再受信で作り直しても送らない          |
