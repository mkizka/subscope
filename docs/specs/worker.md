# Worker仕様

用語は[用語集](../glossary.md)を参照する。

## レコードのインデックス

Tapから受け取ったコミットのレコードをDBに保存・削除する。対象のコレクションは post、repost、like、follow、profile、feed generator、list、listitem、threadgate、postgate。

- index-1: 作成・更新されたレコードを保存する
- index-2: 削除されたレコードを削除する
- index-3: Lexiconのスキーマに合わないレコードはジョブを失敗させずにスキップする
- index-4: null文字を含むレコードは保存しない
- index-5: 削除したレコードは、削除より古いrevのコミットで復活させない
- index-6: 更新したレコードは、更新より古いrevのコミットで古い内容に戻さない
- index-7: revを持たないコミットは、revを比べずに処理する
- index-8: 処理済みのrevと同じrevのコミットは、もう一度処理する
- index-9: threadgate と postgate は、同じアカウントで同じrkeyの投稿を対象とするものだけ保存する
- index-10: レコードの作成者やフォロー先などのアクターは、すでに保存済みでハンドルと状態が変わらなければ更新しない

null文字を含む文字列はPostgreSQLに保存できないため除外する。

コミットは並列に処理され、失敗したジョブはリトライされるため、同じレコードへのコミットが届いた順に処理されるとは限らない。そのためレコードのURIごとに処理済みの最新のrev(リポジトリのコミットを表すTID)を記録する。DBのコミット後、後続のジョブを積む前にジョブが落ちた場合でも、リトライで後続のジョブを積み直せるように、同じrevは古いとみなさない。

アクターの行を更新するとトランザクションのコミットまで行ロックを持ち続ける。Tapのバックフィルでは同じアカウントのコミットが続けて届くため、毎回更新すると並列に処理しても同じ行のロックを順番に待つことになる。そのため変更がないときは更新しない。

コミットのジョブは`COMMIT_WORKER_CONCURRENCY`(既定128)件まで並列に処理し、DBの接続は`DATABASE_POOL_MAX`(既定32)本まで使う。appviewとwebの接続(各10本)と、デプロイ時に新旧のWorkerが並ぶ間を合わせても、PostgreSQLの既定の上限(100本)に収まるようにしている。

threadgate と postgate は専用のテーブルを持たず、レコードのJSONだけを保存する。Lexiconの定めにより対象の投稿と同じrkeyを持つため、appviewは投稿のURIから引ける。

## キュー件数のログ

運用時にジョブの滞留を確認できるように、各キューの件数(waiting、prioritized、active、delayed、failed)を1分ごとにログへ出す。

## Tapへの登録

追跡アクターをTapに登録し、そのレコードを受け取れるようにする。登録状態が変わりうる操作のあとに`syncTapRepo`ジョブを積み、ジョブを実行した時点のDBの状態から登録するか外すかを決める。ジョブはDBのコミット後に積むので、遅らせずに実行する。

- tap-1: サブスクライバーがフォローしたアカウントをTapに登録する
- tap-2: サブスクライバー以外のフォローではTapに登録しない
- tap-3: サブスクライバーがフォローを外したアカウントは、追跡アクターでなくなればTapから外す
- tap-4: 他のサブスクライバーがフォローしているアカウントはTapから外さない
- tap-5: サブスクライバー以外がフォローを外してもTapから外さない
- tap-6: サブスクライバーは、フォローを外されてもTapから外さない

サブスクライバー本人は、AppViewが me.subsco.sync.subscribeServer の時点でTapに登録する。Tapは登録されたアカウントの過去のレコードをバックフィルしてから、以降のイベントを送る。

## ラベルの保存

モデレーションサービスから受け取ったラベルを保存する。

- label-1: 保存済みのアクターと、そのアクターのレコードに付いたラベルを保存する
- label-2: 保存していないアクターへのラベルは保存しない
- label-3: negがtrueのラベルを受け取ったら、同じラベルを削除する
- label-4: Tapに登録したアカウントと、そのアカウントのレコードに付いているラベルをモデレーションサービスの queryLabels で取り寄せて保存する

ラベルは受け取った時点で保存済みのアクターの分だけを保存するため、あとから追跡を始めたアカウントに以前から付いていたラベルは label-4 で取り寄せる。モデレーションサービスは環境変数 `MODERATION_URL` で指定し、デフォルトはBluesky公式の `https://mod.bsky.app`。

## アカウント状態の保存

Tapのidentityイベントが持つアカウントの状態（active、deactivated、deleted、suspended、takendown）をアクターに保存する。

- account-1: アカウントの状態をアクターに保存する
- account-2: 状態が deleted のアカウントは、アクターを削除する

deleted は取り消せないため、アクターと一緒にそのレコードやサブスクリプションも削除する。それ以外の状態は元に戻りうるため、データを残してappviewで隠す。

## ハンドルの解決

ハンドルを持たないか handle.invalid のアクターのDIDドキュメントを`resolveDid`ジョブで解決し、ハンドルを保存する。

- resolveDid-1: DIDドキュメントのハンドルは、そのハンドルが同じDIDに解決できるときだけ保存する
- resolveDid-2: ハンドルが同じDIDに解決できないときは handle.invalid を保存する
- resolveDid-3: すでに handle.invalid 以外のハンドルを持つアクターのハンドルは上書きしない
- resolveDid-4: Tapのidentityイベントのハンドルが handle.invalid のときは、DIDドキュメントからハンドルを解決し直す

DIDドキュメントのハンドルは本人以外も自由に書けるため、公式AppViewと同じくハンドルからDIDへの解決と照らしてから保存する。Tapもidentityイベントで同じ検証をしてハンドルを送るので、すでにあるハンドルはそちらを優先する。ただしTapはハンドルの解決に一時的に失敗したときも handle.invalid を送り、開発環境の`.test`のハンドルは常に解決できないため、handle.invalid だけは自分でも解決し直す。

`ATPROTO_HANDLE_RESOLVER_URL`を設定すると、ハンドルはDNSやHTTPSではなくそのサーバーの`com.atproto.identity.resolveHandle`で解決する。`.test`のハンドルを使う開発環境向けの設定である。

## 統計の集計

いいね数やフォロワー数などの統計を、レコードをインデックスしたあとに集計ジョブで数え直す。集計ジョブは10秒遅らせて実行し、続けて来たイベントを1回の集計にまとめる。

- aggregate-1: 同じ対象の集計ジョブが実行待ちの間に来たイベントは、そのジョブにまとめる
- aggregate-2: 集計ジョブの実行中や完了後に来たイベントは、もう一度集計する

## 通知の生成

レコードをインデックスするときに、サブスクライバー宛ての通知を作る。

- notify-1: 通知はサブスクライバー宛てにだけ作る
- notify-2: 自分自身の操作では通知を作らない
- notify-3: いいねされた投稿の作者に like の通知を作る
- notify-4: リポストされた投稿の作者に repost の通知を作る
- notify-5: フォローされたアカウントに follow の通知を作る
- notify-6: リプライの親投稿を含めて4つ上までの投稿の作者に reply の通知を作る
- notify-7: 引用された投稿の作者に quote の、メンションされたアカウントに mention の通知を作る
- notify-8: 1つの投稿から同じ相手への通知は mention > quote > reply の優先順で1件にする

リプライの祖先は保存済みの投稿だけをたどれるので、未保存の投稿より上の作者には通知しない。

v1.0では次の通知は作らない。

- 追跡アクター以外からの通知。Tapから受信しないため届かない。v1.0後に検討する
- 上記以外のreason（starterpack-joined、verified、like-via-repost、subscribed-postなど）
